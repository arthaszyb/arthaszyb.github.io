## 背景

某天线上一台对外服务的响应时间从 p99 ~80ms 涨到 ~900ms，没有明显的发布记录。本文记录了从告警到定位根因的完整排查过程，按时间顺序整理成一份可复用的检查清单。

### 现象

- 监控面板上 p99 延迟曲线在 14:02 左右开始爬升
- 错误率没有明显变化，只是慢
- 上游负载均衡没有报健康检查失败

### 影响范围

只有一个可用区的两台机器受影响，同集群其他可用区正常，初步怀疑是单机或单可用区问题，而非应用代码本身的回归。

## 第一步：确认是否是资源瓶颈

先看最基础的几个指标，避免一上来就陷入应用层日志的海洋。

```bash
# 整体负载与 CPU
uptime
mpstat 1 5

# 内存与 swap
free -h
vmstat 1 5

# 磁盘 I/O
iostat -xz 1 5
```

输出摘要（节选）：

```text
$ uptime
 14:07:32 up 212 days,  3:41,  2 users,  load average: 18.42, 15.03, 9.77
```

`load average` 明显偏高，而 CPU 核数只有 8，说明大量进程在等待某种资源，而不是纯计算密集。

## 第二步：定位等待的资源类型

### 检查 D 状态进程

`load average` 高但 CPU 利用率不高，通常意味着大量进程处于不可中断睡眠（`D` 状态），多半在等磁盘 I/O。

```bash
ps -eo pid,ppid,state,cmd | awk '$3=="D"'
```

```text
  8821   1234 D nginx: worker process
  8822   1234 D nginx: worker process
  9014   7710 D php-fpm: pool www
```

### 追踪具体卡在哪个系统调用

对其中一个卡住的进程做一次 `strace`，确认它在等什么：

```bash
strace -p 9014 -f -tt -T
```

```text
14:08:03.221011 read(11, ...) = ... <0.842113>
```

单次 `read()` 耗时 842ms，明显异常，指向底层存储或挂载点的问题。

## 第三步：确认存储层

### 检查挂载点与文件系统

```bash
mount | grep data
df -h /data
```

### 检查是否有网络存储抖动

这台机器的 `/data` 是 NFS 挂载，用 `nfsstat` 和 `nfsiostat` 交叉验证：

```bash
nfsiostat 1 5
```

```text
ops/s      rpc bklog
  12.34         3.21
```

`rpc bklog`（RPC 积压队列）不为零，说明客户端在排队等 NFS server 响应——这就是根因方向：NFS server 端某个时间段响应变慢，拖慢了本机所有依赖该挂载点的读写操作，进而顺着调用链传导成应用层的 p99 延迟上升。

## 第四步：临时缓解与后续修复

### 临时缓解

- 把两台受影响的机器从负载均衡摘除，避免继续放大影响
- 观察摘除后集群整体 p99 是否恢复正常

### 根因侧修复

- 联系存储团队确认 NFS server 当时的负载情况
- 评估把这类高频读写路径迁移到本地磁盘或对象存储缓存，减少对单点 NFS 的强依赖
- 补充 NFS 客户端侧的 `rpc bklog` 监控项，下次同类问题能在告警阶段就定位方向

## 检查清单汇总

排查这类"慢但不错"问题时，可以按下面的顺序过一遍：

1. `uptime` / `mpstat` 确认负载与 CPU 使用率是否匹配
2. `vmstat` / `free` 排除内存和 swap 压力
3. `iostat -xz` 看本地磁盘 I/O 是否饱和
4. `ps -eo state` 找 `D` 状态进程，锁定卡住的资源类型
5. `strace -T` 定位具体卡在哪个系统调用、耗时多少
6. 如果涉及网络存储，检查 NFS/远程磁盘的客户端统计（`nfsiostat`、`rpc bklog` 等）
7. 先做流量层面的缓解（摘除节点），再推进根因修复

## 小结

这类问题的关键在于不要一上来就去翻应用日志——先用系统层的通用工具（`uptime`、`vmstat`、`iostat`、`strace`）把"卡在哪一层"缩小范围，再针对性下钻。日常把这套检查清单记熟，能把平均排查时间从几十分钟压缩到几分钟。
